# Repository audit, 2026-10-13

One-shot read-only audit of the whole workspace at commit `672a26f` (branch `Audit`). No code was changed; the only commit on the branch is a one-line refresh of a stale `Cargo.lock` entry. Findings are ranked: correct, safe, holds under load, tested, fast, lean.

**What this repo does:** `sdc` converts a texture artist's source images (PNG, TGA, EXR, ...) into Skyrim DDS files, from a command line or a GUI. The GUI also scans the user's Mod Organizer 2 mod list (NIF meshes, BSA archives, ESP plugins) into a SQLite cache to show which meshes use a texture, and renders a live 3D preview through the user's installed Community Shaders.

**Load assumed:** one artist on one Windows PC. Folders of up to a few thousand textures up to 8K. A mod list of a few thousand mods, 50k to 300k meshes, hundreds of archives and plugins, all from third parties and so possibly corrupt. A 60 fps GUI loop.

**What ran:** `cargo test` and `cargo clippy` for the five crates that build on Linux (nif, vfs, esp, pgpsim, modscan). Clippy is clean. One test fails (finding 18). The engine, CLI, GUI, renderer, bench and encoders are Windows-only and were read, not run. A throwaway fuzz probe (outside the repo) fed every NIF, BSA and ESP fixture through the parsers truncated at every byte and with random bit flips: no panics.

## Must fix

1. **A cancelled scan shows last run's winners as current** (`crates/modscan/src/scan.rs:203-269`, `crates/modscan/src/store.rs:778-791`)
   - **What this is:** The mesh scan marks every origin (mod, archive) disabled at start, then re-enables each one as it is upserted. Winner rows (which copy of a mesh the game uses) are only rewritten at the end. Each chunk is its own transaction; nothing marks "scan complete".
   - **Problem:** User enables mod X, which overrides mod Y's `a.nif`, starts a scan and cancels (or PGPatcher starts mid-scan, which ends the scan early and the GUI reloads). The store now has X enabled with its copy row written but the winner still pointing at Y. The Meshes view shows Y as "Wins" and X as "Overridden", and planning votes mix both. After a restart nothing says the data is from a cancelled run. The GUI comment at `meshes.rs:736` ("origins are outside the run until a scan completes") is false: they are enabled again a millisecond after `begin_scan`.
   - **Fix:** Upsert origins with `enabled = 0` during the run and flip them in one `UPDATE origin SET enabled = 1 WHERE id IN (...)` right before `delete_unseen` (pass it the id list). A cancelled run then leaves every read query empty, which is what the GUI already claims. Add a test that cancels mid-parse after a mod-list change and asserts the lists are empty.
   - **If we skip it:** Stale winners presented as current after any cancel or PGPatcher overlap.

2. **A corrupt BSA folder count allocates about five times the file size** (`crates/vfs/src/bsa.rs:82-90`)
   - **What this is:** The archive reader trusts each folder's file count and pushes one record per count until end of file; the only check (`recs.len() != nfiles`) runs after the loop.
   - **Problem:** One flipped byte makes a folder say 0xFFFFFFFF files. Measured: a 132 MB archive took 2.3 s and 600 MB of RAM before failing with "failed to fill whole buffer". A 3 GB texture archive with the same damage needs 15 GB and kills the GUI during the scan, which opens every archive.
   - **Fix:** After reading `counts`, `if counts.iter().sum::<usize>() != nfiles { return Err(Corrupt("file count mismatch")) }` and delete the now unreachable post-loop check. Add a test with a hostile count asserting `Corrupt` before any read.
   - **If we skip it:** One bad archive in the mod list ends the scan with an out-of-memory crash instead of a "corrupt archive" row.

3. **A hostile NIF string count allocates about six times the file size** (`crates/nif/src/header.rs:71-75`)
   - **What this is:** The header parser caps `nblocks` but not `nstrings`, and collects that many strings.
   - **Problem:** A file declaring `nstrings = 0xFFFFFFFF` followed by zeros reads 4-byte empty strings until the buffer ends, each costing a 24-byte `Vec`. Measured: a 64 MB file took 400 MB before failing. The scan parses NIFs on all cores, so several such files multiply this.
   - **Fix:** `if nstrings > MAX_BLOCKS { return Err(...) }` before the collect; real files have under a thousand strings.
   - **If we skip it:** A handful of damaged meshes push the scan toward out-of-memory.

4. **The NIF graph cycle check is quadratic, so a long chain freezes the 3D preview** (`crates/nif/src/graph.rs:220-232`)
   - **What this is:** For every child edge, `reaches` walks the parent's whole ancestor chain to detect a cycle, with no cap; `depth` and `world` already stop at `MAX_DEPTH`.
   - **Problem:** A mesh with N nodes each the child of the previous costs N²/2 lookups. Measured in release: 10k nodes 1.1 s, 20k 4.8 s, 40k (3.5 MB) 21 s. `MAX_BLOCKS` is 2^20, so an 88 MB hostile mesh opened in the preview blocks for hours. Only the preview calls `read_graph`, so the scan is unaffected.
   - **Fix:** Stop the walk in `reaches` after `MAX_DEPTH + 2` hops and return `false`. Both existing cycle tests still pass.
   - **If we skip it:** An oversized or malicious mesh hangs the preview thread.

5. **"Up to date" never looks at the output file** (`crates/engine/src/api.rs:549-595`, `:1668-1687`)
   - **What this is:** Under the default `--on-existing if-changed`, an existing output is kept when the manifest's last record matches the current source hash, profile hash and encoder versions.
   - **Problem:** The artist or another tool overwrites `out/rock.dds`, or a copy truncates it. The manifest still matches, so every later run says "up to date" and ships the wrong bytes. Ruling O2 already wanted a failed output re-encoded rather than trusted; a replaced output is the same spirit.
   - **Fix:** `SourceStamp` already exists (`policy.rs:1160-1180`). After the rename in `process_file`, store `SourceStamp::of(&job.output)` in a new `#[serde(default)] output_stamp` field of the manifest record and require it to match in `is_up_to_date` (metadata only, no hashing; a record without the field counts as stale once).
   - **If we skip it:** A modified or damaged output is kept as current until the profile or engine changes.

6. **One unreadable folder entry aborts the whole batch** (`crates/engine/src/discover.rs:105-106`)
   - **What this is:** The recursive walk uses `?` on every directory entry; the error becomes `EngineError::Usage`, exit 2.
   - **Problem:** `sdc convert textures --recursive` where one subfolder is access-denied, a dangling junction or a cloud placeholder: "discover: Access is denied", exit 2, nothing converts. Load, analyse and resolve isolate per-file failures; discovery does not.
   - **Fix:** `let Ok(e) = e else { continue }` and return the skipped paths so `plan` emits one warning per entry; the batch continues.
   - **If we skip it:** One bad folder blocks a whole export.

7. **The Sets column rebuilds every set view and the whole export plan every frame** (`crates/gui/src/ui/sets_column.rs:106-110`, `crates/gui/src/model/sets.rs:360-470`, `crates/gui/src/model/pbr_export.rs:250-328`)
   - **What this is:** Each frame calls `set_views(model)` and `export_blocks(model)`; `export_blocks` calls `set_views` four to six more times and builds and schema-validates the full JSON. `set_views` re-parses every set entry from TOML (`toml_to_json` runs `toml::from_str` per value) and finds each member by a linear scan (`AppModel::item`).
   - **Problem:** 3000 textures in about 1000 sets: per frame roughly 8 × (3000 × 3000 string compares + 1000² `same_id` + ~10k TOML parses), at 60 fps. The UI drops to a few frames per second whenever the Sets column is visible. `request()` and `EngineInputs::of` pay the same cost four times per re-plan.
   - **Fix:** Cache `Vec<SetView>` and the export blocks on `AppModel`, invalidated in `apply_plan` and `edit_docs` (the only two places the inputs change); build a key-to-index `HashMap` in `apply_plan` and use it in `item()`.
   - **If we skip it:** The GUI is unusable at the stated folder sizes.

8. **Thumbnails are copied per plan, never evicted, and never freed from the GPU** (`crates/engine/src/session.rs:146-183`, `crates/gui/src/model/items.rs:220,239`, `crates/gui/src/ui/thumbs.rs:19-39`)
   - **What this is:** The engine cache keeps a 256×256 RGBA thumbnail (256 KB) per file for the session and never removes one. `PlanView::build` clones each thumbnail into every `TextureItem` on every re-plan (after every edit). `ThumbCache` keeps one egui texture per key forever and hashes the full RGBA of every visible tile every frame to detect changes.
   - **Problem:** 3000 textures: about 786 MB in the engine cache, another 750 MB copied per re-plan (three copies coexist during `apply_plan`), plus 750 MB of GPU textures after one scroll that are never released. Opening a second folder adds on top. Per frame, hashing ~24 visible tiles costs 4 to 6 ms of the 16 ms budget.
   - **Fix:** Store `Arc<Thumbnail>` in the cache and in `TextureItem`; `retain` the cache to the paths of the current plan at the end of `plan_cached`; clear `ThumbCache` when `model.items` is replaced and key the change check on the `Arc` pointer instead of hashing the pixels. Optionally shrink thumbnails to 128 px (4× less).
   - **If we skip it:** Memory grows with every folder opened until the GUI dies on a 16 GB machine; every edit stalls on memcpy.

9. **A re-run hashes every source on one thread before any conversion starts** (`crates/engine/src/api.rs:1627-1720`)
   - **What this is:** The on-existing decision loop runs on the calling thread before the thread pool is built, and for each job with an existing output SHA-256s the source (and every pack, bake and RNM source). Files found stale are hashed again in `process_file`.
   - **Problem:** A re-run over 3000 sources averaging 20 MB with outputs present hashes about 60 GB serially: one to two minutes with no progress events, the pool idle and the GUI run frozen. This is the dominant cost of a no-op re-run.
   - **Fix:** Compute the decisions with `ready.par_iter()` inside the pool, then emit the skip events from the serial loop as now; pass the computed source hash into `process_file` so it is not recomputed.
   - **If we skip it:** Every `if-changed` re-run on a large folder stalls for minutes before the first `file_started`.

10. **Undo merges across an undo boundary and loses a step** (`crates/gui/src/model/history.rs:40-49`, `:72-83`)
    - **What this is:** A push with a merge key folds into `undo.last()` whenever that command has the same key, regardless of what happened in between.
    - **Problem:** Type JSON name "x" (A), change a shader (B), type "y" (C); Ctrl+Z twice (C and B move to redo, A is on top); type "z" → merged into A, so `A.after = "z"` and redo is cleared. Ctrl+Z now jumps from "z" to the state before A; the "x" state the user had as a step is gone. Same for every `set:key` slider merge.
    - **Fix:** In `undo_step` and `redo_step`, set `merge = None` on the command that becomes the new top of `undo` (two lines), so a merge only continues an uninterrupted run of edits.
    - **If we skip it:** Undo occasionally skips a step after an undo and retype.

11. **"Accept all suggestions" spawns one plan thread per decision and cannot be undone past 200** (`crates/gui/src/model/mod.rs:720-751`, `crates/gui/src/model/history.rs:58-69`)
    - **What this is:** Each pick goes through `decide`, which pushes a history step and calls `replan()`; afterwards `fold_last(n)` is meant to merge the steps into one.
    - **Problem:** 300 undecided textures → 300 plan threads in one click, each cancelling the previous, but `discover` has no cancel check, so every one walks and stats the whole folder first: seconds of CPU and 300 OS threads. And `fold_last` returns without folding when `n > History::LIMIT` (200) or when the list was already trimmed, so the user gets 200 separate undo steps and the first picks cannot be undone at all. The existing test uses a small fixture, so it passes.
    - **Fix:** Take one snapshot before the loop, apply the decisions with `replan = false`, push a single command, then `replan()` once. Add a test with more than 200 picks.
    - **If we skip it:** A long stall on the one button meant to save time, and an undo history that lies.

12. **A detail normal layer at strength above 1 writes normals pointing into the surface** (`crates/engine/src/rnm/blend.rs:24-32`, range at `crates/engine/src/policy.rs:1290`)
    - **What this is:** `decode` turns a stored layer texel into a tangent vector with `z = |t.z| + 1 − s`; policy allows `rnm.<layer>.strength` up to 2.
    - **Problem:** For s > 1, any texel whose stored blue is below `1 − 1/(2s)` gets negative z. Example: stored (0.99, 0.5, 0.6), strength 1.5 → z = 0.3 + 1 − 1.5 = −0.2 → normalised (0.99, 0, −0.135) → quantised B = 110 (< 128). Mip 0 of the `_n` carries normals under the surface on every steep detail texel; nothing clamps z after the blend (the `z.max(0)` in `ops.rs:172` runs before `apply`), and renormalisation keeps them.
    - **Fix:** `(t[2].abs() + 1.0 - s).max(0.0)` (one call), or cap strength at 1. Add a test: `decode([0.99,0.5,0.6,1.0], 1.5, false)[2] >= 0.0`. Confidence medium: the reference `rnm.py` was not available to confirm its s > 1 behaviour.
    - **If we skip it:** Artists who push a detail slider past 1.0 get lit-from-below texels along edges with no warning.

13. **The coverage check cannot fire under `validation.mips = smallest`** (`crates/engine/src/validate/mod.rs:320-322`, `:328`)
    - **What this is:** The per-level coverage loop skips every level but the last when `smallest` is set (the `fast-preview` preset), and then `COVERAGE_MIN_TEXELS = 256` skips any level smaller than 256 texels.
    - **Problem:** Every full chain ends at 1×1, so under `smallest` the only level visited is 1×1 and the 256-texel guard always fails. `VAL-COVERAGE` can never fire, and `summary.coverage` holds exactly one entry (0.0 or 1.0), which the GUI shows as the coverage figure. A 1024² cutout whose 32² mip dropped from 20% to 5% coverage validates clean. The skip saves nothing: all levels are already decoded and `coverage_fraction` is one cheap pass.
    - **Fix:** Delete the three-line `Smallest` skip in the coverage loop (keep the PSNR shortcut, which is what Note T5 asked for).
    - **If we skip it:** The preview preset reports a meaningless coverage number and misses the one drift it exists to catch.

14. **Shader recompiles on a loaded mesh are invisible and their failures are silent** (`crates/gui/src/model/viewport3d.rs:1773-1775`, `:2011-2017`, `:744-755`; `crates/gui/src/app.rs:244-249`)
    - **What this is:** The render thread never sends `V3Reply::Shapes` for `Content::Mesh` (plan P1B assumed mesh content never has pending shapes), but toggling "Community Shaders features" or a CS settings define runs `begin_all` in async mode, which does make mesh shapes pending or failed.
    - **Problem:** In the Meshes view, untick the features toggle: shapes go pending and compile in the pool, `busy()` stays false, no spinner, no repaint request, so the new picture waits in the channel until the mouse moves. If the new permutation fails to compile (old CS build), the shape becomes `Failed { showing_previous: true }` and nothing lists it: `problems()` only shows the original load's errors. The user keeps the old image with no error.
    - **Fix:** Drop the two `!matches!(.., Content::Mesh(_))` guards so `Shapes` is sent for every content, and have `ui/viewport3d.rs::problems()` also list shapes in `Failed`. Add a test: mesh loaded → `Shapes([Pending])` → `busy()`; `Shapes([Failed])` → error visible.
    - **If we skip it:** Feature and settings toggles in the Meshes view look dead; compile failures after a toggle are silent.

## Should fix

15. **`--sidecar` writes nothing for an up-to-date output** (`crates/engine/src/api.rs:1674-1687`, `crates/engine/src/pipeline.rs:484-497`)
    - **What this is:** The sidecar JSON is only written inside `process_file`, as a by-product of encoding.
    - **Problem:** Run once without `--sidecar`, then again with it and nothing changed: every file is "up to date", zero `.dds.json` appear, exit 0. The flag is documented as "also write `<name>.dds.json` next to each output".
    - **Fix:** In the up-to-date branch, when `req.sidecar` is set and the sidecar is missing, `write_atomic` the stored record (`e.raw`). Five lines, no re-encode. Also set `req.sidecar = true` in the existing "failed manifest append removes the output" test so the sidecar cleanup branch is exercised.
    - **If we skip it:** Users who turn sidecars on later get them only for files that happen to change.

16. **Non-ASCII MO2 paths decode wrongly from `@ByteArray(...)`** (`crates/modscan/src/qtini.rs:6-16`)
    - **What this is:** `unquote` strips the `@ByteArray(` wrapper and un-doubles backslashes, nothing else. Qt serialises a byte array by reinterpreting bytes as Latin-1 (Qt 6) or as `\xHH` escapes (Qt 5).
    - **Problem:** A game path `D:\Spiele\Skyrim SE – Stock` or a user folder `C:\Users\José\...` comes back as `JosÃ©` or `Jos\xe9`, so `game_data` points at a folder that does not exist: vanilla archives and Data loose files silently absent, plugins "not found in the game Data folder". The existing test only covers ASCII.
    - **Fix:** After unwrapping, map chars U+0080..U+00FF back to single bytes and `\xHH` to bytes, then `from_utf8_lossy`. About 10 lines; add a test with an accented path. Confidence medium on the exact Qt encoding; the failure is certain for either.
    - **If we skip it:** Any non-ASCII instance or game path scans an empty Data folder with no error.

17. **Two scans on the same `scan.db` destroy each other's rows** (`crates/modscan/src/store.rs:727-732`, `crates/modscan/src/scan.rs:573`)
    - **What this is:** `Store::open` is a plain WAL connection with a 5 s busy timeout; nothing marks a scan in progress.
    - **Problem:** Two GUI instances share `%LOCALAPPDATA%\sdc\scan.db`. One scans a folder, the other the MO2 instance. The folder scan's `delete_unseen` deletes every copy of an enabled origin not in its own `seen` set; the MO2 scan's origins are enabled (finding 1), so its rows vanish mid-run and it ends with "copy row missing after scan" after minutes of work.
    - **Fix:** Hold an exclusive lock on a sibling `scan.lock` file for the duration of `run_with` (`std::fs::File::try_lock` needs rust-version 1.89) and return a new `ScanError::Busy` on contention.
    - **If we skip it:** Rare, but the outcome is a lost cache and a confusing error after a long scan.

## Nice to have

21. **The base level is held twice across mipmaps and quantise** (`crates/engine/src/mips.rs:178-179`, `crates/engine/src/pipeline.rs:260-294`)

    - **Problem:** An 8192² source peaks at about 2.9 GB, of which 1.07 GB is the duplicate; at 16384² the duplicate is 4.3 GB. The budget (64 B/px) covers it, so nothing breaks, but fewer files are admitted in parallel.
