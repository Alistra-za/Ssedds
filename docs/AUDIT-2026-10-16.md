# Audit 2026-10-16: whole repo at main b5ad038

**What this repo does:** Tessalith turns a modder's source images (PNG, PSD, EXR and more) into DDS texture files that Skyrim loads correctly. It has a command-line tool (`sdc`), a desktop GUI (`tessalith.exe`), a shared engine that does the real work, and readers for the game's own files (meshes, archives, plugins) so the GUI can see how a texture is used in a mod setup. **Load assumed:** one modder on one Windows PC, running on folders of hundreds to a few thousand textures, with parallel worker threads and background GUI threads. Inputs are files downloaded from the internet, so a bad file must never crash the tool or eat all memory.

The code is in good shape. The parsers for hostile files are bounded and tested, every file write but one goes through a safe temp-and-rename, and the 60 `unsafe` blocks in the FFI and the Direct3D renderer hold their invariants. What is left is one real bug for script users, a handful of wrong results in corner cases, and several places where the work done per frame or per plan grows with the square of the project size.

## Must fix

1. **Piping `sdc` output into `head` or a pager makes it exit as "crashed"** (`crates/cli/src/verbs.rs`, 53 `println!` sites; `crates/cli/src/main.rs:77-86`)
   - **What this is:** The report verbs (`inspect`, `validate`, `presets`, `encoders`, `patch-header`) print with `println!`. In Rust, `println!` panics when the write fails. A reader that stops early (`head -n1`, `Select-Object -First 1`, a pager you quit) closes the pipe, so the next write fails.
   - **Problem:** `sdc validate *.dds --json | head -n1`: after the first line the next print panics, `main` catches it, prints `sdc: internal error` and returns exit code 3, the code reserved for a fatal failure. A script checking the exit code treats a healthy run as a crash. The engine's own JSON sink already ignores write errors; the verbs' lines do not.
   - **Fix:** One stdout writer that ignores errors: a tiny macro `out!` doing `let _ = writeln!(std::io::stdout().lock(), ...)`, and replace every `println!`/`print!` in `verbs.rs` with it (`say()` at `verbs.rs:590-596` the same way). Add one test that spawns `sdc validate a.dds b.dds --json` with a piped stdout, drops the read end before waiting, and asserts the exit code is 0 or 4, not 3.
   - **If we skip it:** Every pipeline that pipes `sdc` into a pager or `head` reports a fatal error; `sdc validate --json | jq -e` misreports in scripts.

## Should fix

2. **Edits made while an export runs are written to disk behind the user's back** (`crates/gui/src/model/mod.rs:1491-1507`, `cs_pbr_export.rs:293-302`, `cm_json.rs:486-495`)
   - **What this is:** After a clean export the GUI stores a hash of the JSON it wrote into `sdc-project.toml` and saves that whole file. Set edits (`sets_editable()` checks only read-only, not busy) and Undo/Redo stay enabled while an export runs.
   - **Problem:** Press Export (both project files are saved), press Ctrl+Z twice while it runs, export ends. The hash record saves `sdc-project.toml` with the two steps undone. The user never pressed Save. "Discard" on close cannot bring the file back, and `sdc.toml` on disk still holds the exported state, so the two files disagree.
   - **Fix:** In all three finish paths, read `let was_dirty = d.is_dirty();` before storing the hash. When dirty, skip `d.save(false)` and note "hash recorded; written with the next Save". The in-memory hash is still right; a stale on-disk record only makes the next export ask before overwriting its own file. One test: edit a set after `export_clicked()`, wait, assert the file on disk lacks the edit.
   - **If we skip it:** The user's "unsaved" edits are sometimes already on disk, and the Discard button lies.

3. **Writing output next to the sources converts nothing and says nothing** (`crates/engine/src/discover.rs:111-139`)
   - **What this is:** Discovery skips anything under the output root, so the tool never reads back what it wrote. The test is "is this path under the output root", which is also true when the output root is the input folder itself.
   - **Problem:** `sdc convert textures -o textures` (write the `.dds` beside the `.png`, a common in-place layout): every source is "under the output root", zero inputs are found, exit 0, no message. The one real in-place hazard (overwriting a source DDS) is already guarded separately at `api.rs:989`.
   - **Fix:** Apply the skip only when the output root is strictly inside the input folder: `if out_abs != in_abs && is_under(&out_abs, &in_abs)`. Or, if in-place is meant to be unsupported, return a usage error from `plan`. Either is one `if`; zero inputs with exit 0 is wrong either way. Add a test with output root equal to the input folder.
   - **If we skip it:** Users running in place conclude the tool is broken.

4. **Complex grass gets a false coverage warning** (`crates/engine/src/pipeline.rs:283-285`, `validate/mod.rs:343-367`)
   - **What this is:** Coverage preservation keeps the share of texels that pass the alpha test the same at every mip. Complex grass is one image with colour on top and a normal map below; its top half is preserved in `grass::build`, its bottom half's alpha is specular data and is just averaged.
   - **Problem:** The base coverage is measured on the whole stacked image, and every stacked mip is compared with it. A grass normal whose specular alpha varies around the threshold passes 50% at mip 0 and drifts toward 0% or 100% at mip 3. The stacked share moves by up to 25 points while the top half is exactly right, so a correct texture gets `VAL-COVERAGE` on its low mips.
   - **Fix:** `let base_coverage = if grass { None } else { base_coverage(&chain[0], p, alpha_present) };`. One test in `tests/complex_grass.rs`: a source whose bottom-half alpha alternates 100/160 yields no `VAL-COVERAGE`.
   - **If we skip it:** Grass packs with varying specular show warnings users learn to ignore.

5. **A second scan after running PGPatcher stalls, and vanilla sources stay "unverified" forever** (`crates/modscan/src/scan.rs:395-420, 644-656`)
   - **What this is:** PGPatcher output is checked for staleness by comparing a checksum (CRC32) of the source mesh with the one PGPatcher recorded. The parallel parse pass computes it only for meshes it parses. A mesh reused from the cache (same size and date) keeps the cache's CRC, which is empty when the earlier scan had no PGPatcher output. Step 6 then fills the gap with `crc_of`, which reads each file one at a time on the scan thread and returns nothing for a mesh inside a BSA archive.
   - **Problem:** The normal flow is scan, run PGPatcher, scan again. Every source was cached without a CRC, so `crc_of` reads thousands of meshes serially after the parallel pass, with progress stuck. For a source inside a BSA (every vanilla mesh PGPatcher patches) it gives nothing, so the patched copy is "unverified" and stays so on every later scan, since the reuse path never reads it again. The same copy gets "match" on a cold cache and "unverified" on a warm one.
   - **Fix:** Do not reuse a candidate that has no CRC; let the parallel pass hash it (it already hashes BSA entries): add `&& !(candidate[i] && m.crc32.is_none())` to the reuse arm. Then `crc_of` is a map lookup and its `fs::read` fallback, `new_crcs` and the `crcs` parameter of `Store::set_derived` can go. Add the missing test: scan, then add a PGPatcher output, scan again, assert `reused == 1` and the row says "match"; a variant with the source in a BSA.
   - **If we skip it:** One long stall per "scan after PGPatcher" and a wrong badge on every vanilla-source patched mesh. Nothing in the test suite exercises this path.

6. **Planning a half-finished PBR pack makes millions of file-system calls** (`crates/engine/src/bake/plan.rs:91-113`, callers around `:395` and `:454`)
   - **What this is:** When a PBR set has a normal map but no roughness map (or the reverse), `sibling_outside` lists the folder and calls `p.is_file()` (one metadata call) on every entry to find a companion outside the batch. It runs once per such set, on every plan.
   - **Problem:** A flat folder of 4500 files where 1500 normals have no roughness yet: 1500 × 4500 = 6.75 million metadata calls per plan. At a few microseconds each that is tens of seconds, and the GUI replans after every set edit. The cheap `batch.contains(p)` test runs after the expensive call.
   - **Fix:** Take the file type from the directory entry and test batch membership first: `.filter(|e| e.file_type().is_ok_and(|t| t.is_file())).map(|e| e.path()).filter(|p| !batch.contains(p))`. To stop re-listing, read each folder once into a map built lazily in `plan_bakes`.
   - **If we skip it:** Planning stalls for tens of seconds on packs in progress.

7. **A typo in a glob pattern silently matches nothing** (`crates/engine/src/policy.rs:148-175`, `overrides.rs:316-345`, `presets.rs:668-684`, `api.rs:2107-2230`)
   - **What this is:** Rules and `--set file:<glob>` pick files with a glob. Globs compile lazily in `glob_match_input`; one that fails to compile is cached as "no matcher" and treated as "matches nothing".
   - **Problem:** `--set 'file:**/armor/[.format=bc1'` (an unclosed bracket) or a preset rule with an unbalanced brace passes `parse_set`, `check_preset` (`sdc presets validate`, the GUI preset editor) and `check_up_front`, since only `policy.rs` ever compiles a glob. The batch runs, exit 0, and the override applies to zero files with no message. The user believes armour is BC1; it is BC7.
   - **Fix:** Compile once where patterns enter: in `parse_set` for the file scope and in `check_preset`/`check_up_front` for each rule glob, `globset::Glob::new(g).map_err(...)` into a usage or preset error. Five lines; the lazy cache stays.
   - **If we skip it:** A glob typo can only be found by inspecting every job's provenance.

8. **`-inf` or `nan` in a setting is silently ignored** (`crates/engine/src/overrides.rs:277-283`, `presets.rs:338-356`)
   - **What this is:** `parse_value` reads the right-hand side as TOML and converts it to JSON. TOML accepts `inf`, `-inf`, `nan`; serde_json turns a non-finite float into `null`, and the merge ignores a null.
   - **Problem:** `--set validation.min_mip_psnr_db=-inf` (the obvious way to switch the PSNR warning off) passes every check, the batch runs, and the threshold stays 30 dB with provenance `builtin`. The same for a `[files]` entry.
   - **Fix:** After the conversion, `if v.is_null() { return Err("not a finite number") }`; reject null leaves in `file_entries` the same way. Six lines.
   - **If we skip it:** A setting the user typed does nothing, without a word.

9. **Every set lookup in the GUI re-parses the whole sets document and stats the scan database** (`crates/gui/src/sets_doc.rs:404-410` and its 29 callers; `crates/gui/src/model/mod.rs:1764-1777`)
   - **What this is:** `SetsDoc::entries()` walks every `[[sets]]` table and converts each value through a format-then-reparse step. Five helpers call it and keep one set. The set-view cache key also includes a file-stamp of the scan database, so every key check is a file-system call; `views()` has 52 call sites and the set editor goes through it several times per frame.
   - **Problem:** With 300 sets and 150 edited entries, one export-blocks rebuild is about 300 full document parses, around a second on the UI thread, and it reruns on every edit and every plan. The set editor parses the document about six times per frame on top, plus tens of metadata calls per frame doing nothing.
   - **Fix:** Cache the parsed entries on the document keyed by its revision, which every mutator already bumps (`entries_cache: RefCell<Option<(u64, Arc<Vec<SetEntry>>)>>`). Replace the file stamp in the view key with a counter bumped where the app already reacts to a finished scan.
   - **If we skip it:** The set editor slows down with the square of the set count; a few hundred edited sets stall per keystroke.

10. **The Sets column lays out every set every frame and scans all sets once per set** (`crates/gui/src/ui/sets_column.rs:140-205, 578-592`)
    - **What this is:** The column draws its set pills in a plain scroll area, so layout runs for every pill each repaint whether visible or not (immediate-mode UI). Inside each pill the recipe lines are found with a linear scan of `model.sets`. The Textures column was virtualised for this reason; this one was not.
    - **Problem:** 800 sets: about 10,000 widgets laid out and 640,000 string compares per repaint. While the user orbits the 3D preview at 60 repaints a second, most of the frame budget goes to a column that did not change.
    - **Fix:** Carry the recipes on the `SetView` (built from `m.sets` already), and skip layout for pills whose last-frame rect is outside the clip rect by allocating their remembered height instead.
    - **If we skip it:** Every drag in the app stutters once a project passes a few hundred sets.

11. **Delete-section matching runs over every set on every frame** (`crates/gui/src/ui/set_editor.rs:123-141`, `json_editor.rs:154`; `model/sections.rs:108-150`)
    - **What this is:** `delete_hits` decides which PGPatcher delete sections hit which sets. It is not cached. The set editor calls it every frame and throws away every hit but the selected set's; the JSON editor calls it every frame too.
    - **Problem:** Five delete sections and 800 sets: about 4000 set visits and 20,000 to 30,000 string allocations per frame while a set is selected, for a result that does not change between frames.
    - **Fix:** Cache it in `ViewCache` keyed by `view_key()` like `export_blocks`, or compute it for the one selected set.
    - **If we skip it:** Fine without delete sections; with them the set editor slows with the set count.

12. **Path keys are lower-cased by two different rules** (`crates/engine/src/group.rs:193` and others use Unicode `to_lowercase`; `crates/nif/src/path.rs:42`, `engine/discover.rs`, `engine/grass.rs`, `modscan/store.rs`, `render3d` use `to_ascii_lowercase`; 17 named helpers plus 64 inline `.replace('\\', "/")` sites in total)
    - **What this is:** A texture is matched to the meshes and records that use it by a normalised path key. The engine's grouping key folds case with Unicode rules; the mesh reader, the scan store and the renderer fold ASCII only.
    - **Problem:** A folder named `Ärger` gives `ärger` as the engine key and `Ärger` as the scan key, so its textures get no mesh evidence (no alpha meaning, no shader votes) and the Meshes filter cannot find it (`store.rs:1389-1397` uses a third variant). Rare in Skyrim paths, but it is one rule written 81 times, and the two spellings already disagree.
    - **Fix:** Keep `nif::path::slashes_lower` for game paths and make `engine::group::fold` public for keys, pick one case rule for both, and delete the GUI copies (`lower` ×3, `path_lower`, `slash`, two `base_of`, six extension strippers with four separator rules).
    - **If we skip it:** Two rules that must agree keep drifting, in two crates.

13. **The most-used texture upload path has no test** (`crates/render3d/src/textures.rs:360-404`; test helpers only build single-mip RGBA8 files)
    - **What this is:** `load_dds_as` turns a DDS into a Direct3D texture, computing one data pointer and row pitch per face and mip. Every real game texture (BC1/3/5/7 with a full mip chain, cube maps) goes through this arithmetic.
    - **Problem:** Direct3D does not check pitch or length against the pointer. A wrong face offset or a pitch in texels instead of blocks uploads garbage or reads past the buffer with no error, and nothing in the suite would notice. The code is right today by reading.
    - **Fix:** One test: an 8×8 BC1 DDS with four flat-colour mips (a flat BC1 block is 8 bytes), loaded and rendered at two sizes that sample mip 0 and mip 3, asserting the two colours; the same helper with the cube flag.
    - **If we skip it:** A silent regression in the one path real textures use.

14. **The `tex_copy` table is rewritten every scan and never read** (`crates/modscan/src/store.rs:43, 1203-1225`; `scan.rs:604-624`)
    - **What this is:** `set_textures` deletes and re-inserts one row per texture copy per mod on every scan. The only readers are three tests; the GUI uses `tex_winner`.
    - **Problem:** A big instance has 200,000 to 400,000 texture copies: that many deletes and inserts per scan for nothing, and a table in the schema that looks load-bearing.
    - **Fix:** Drop the table, the `copies` parameter and first loop of `set_textures`, and `tex_rows` in `scan.rs`; adjust the three tests; bump `SCHEMA_VERSION`. About 25 lines go.
    - **If we skip it:** A second or two per scan and misleading schema.

15. **Two copies of the TOML file state machine** (`crates/gui/src/project.rs:140-215, 499-514` and `sets_doc.rs:200-295`)
    - **What this is:** `ConfigDoc` (for `sdc.toml`) and `SetsDoc` (for `sdc-project.toml`) each carry about 70 lines of the same logic: load, dirty flag, revision, read-only, reload-on-focus, atomic save.
    - **Problem:** They already drift on when the revision counter is bumped, so a fix to one (such as finding 2) must be remembered for the other.
    - **Fix:** One `TomlFile` struct holding the shared state, wrapped by both. About 70 lines go.
    - **If we skip it:** Near-copies that must change together.

## Nice to have

16. **`sdc presets export --out` can destroy an existing hand-edited preset** (`crates/cli/src/verbs.rs:936-939`)
    - **What this is:** The only write in the project that uses plain `std::fs::write` instead of the temp-and-rename helper. `fs::write` truncates first.
    - **Problem:** Exporting onto an existing file that is not a loaded preset, with a full disk or a kill mid-write, leaves a zero-byte or half file. The old file is gone.
    - **Fix:** `engine::dds::write_atomic(&p, text.as_bytes())`, already imported. One line.
    - **If we skip it:** Rare but unrecoverable loss of the one file type users hand-edit.

17. **The published config schema rejects files the GUI writes** (`crates/engine/src/schemas.rs:216-240`; `schema/config.schema.json`)
    - **What this is:** The JSON Schema for `sdc.toml` is meant for editors. Its `[files]` entry definition forbids unknown keys, but the loader accepts `reencode` and `rnm.target` there, and the GUI writes `rnm.target`.
    - **Problem:** A valid `sdc.toml` from the GUI shows as invalid in any editor wired to the schema. The drift test passes because the generator itself is wrong, not stale.
    - **Fix:** Add `reencode` and an `rnm.target` enum to the `[files]` schema and regenerate; one test asserting every path in `FIELD_PATHS` except `subtype` exists in the schema.
    - **If we skip it:** The schema cannot be trusted as documentation of `[files]`.

18. **One hung `nvcompress.exe` hangs the whole batch** (`crates/engine/src/nvtt.rs:283-285, 398-415`)
    - **What this is:** The NVTT probe kills a program that does not answer in 5 seconds, but the per-level encode waits forever and only stops on cancel. All NVTT levels share one slot.
    - **Problem:** An `nvcompress` that hangs (driver, antivirus holding the exe) blocks its worker, and since the slot is held every other NVTT file waits. An unattended CLI batch never ends and never names the file.
    - **Fix:** A generous ceiling scaled by size in the wait loop, then `child.kill()` and report `ENC-NVTT-FAILED` like any other failure.
    - **If we skip it:** One stuck process turns a batch into a hang instead of one failed file.

19. **`write_atomic` flushes every output and every sidecar to disk** (`crates/engine/src/dds.rs:351-353`)
    - **What this is:** Each write calls `sync_all` before the rename, twice per file with `--sidecar`.
    - **Problem:** On a hard disk a flush is 10 to 30 ms: 3000 outputs with sidecars is one to three minutes of pure flushing. After a power loss a torn output already has a different stamp than its manifest record, so `if-changed` re-encodes it anyway, and the manifest itself is not flushed.
    - **Fix:** Delete the `sync_all` line.
    - **If we skip it:** Hard-disk users wait a minute or two longer per large batch.

20. **Two generations of the TOML parser and two dependencies the standard library covers** (`Cargo.toml:17` `toml = "0.8"`, `crates/gui/Cargo.toml:26` `toml_edit = "0.25"`; `hex` in 5 manifests; `encoding_rs` in `nif`)
    - **What this is:** `toml 0.8` drags in the old `toml_edit 0.22`, `winnow 0.7` and three more crates while the GUI's editor and a test crate already use the new chain. `hex` is 15 calls to `hex::encode`; `encoding_rs` does one Windows-1252 decode, which is Latin-1 plus a 32-entry table.
    - **Problem:** Six redundant crates compiled into every build, two TOML grammars in the shipped exes, two places to patch a parser bug.
    - **Fix:** `toml = "1"` in the workspace (the 20 `toml::` items used are unchanged in 1.x), a 4-line `hex_lower` helper, a 32-entry table for the decode. Cannot be proven to compile from this Linux container.
    - **If we skip it:** Nothing breaks; the build stays heavier for good.

About 70 smaller findings were left out (a stale doc comment on `patch-header`, a `winners` parameter that is `|_| false` at every production call, four write-only database columns, a dialog text box that refills itself when emptied, a poisoned-lock `unwrap` in the RNM section, five never-evicting caches, a hand-built DDS header beside the engine's writer, and more). The per-subsystem lists are not kept in the repository.

**Verdict:** Healthy core, one real bug for script users. Fix 1 first (an hour), then 2, 3 and 4 (wrong results), then 5 and 6 (the two stalls). The rest can ride normal work.

**Lean:** about -700 lines, -2 dependencies possible, plus 6 transitive crates if the TOML versions are unified.
