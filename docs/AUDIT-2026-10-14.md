# Repository audit, 2026-10-14

Read-only audit of the whole workspace at commit `ddae78d` (branch `Audit`). Nothing in the code was changed.
Every finding below was checked against that commit by hand.

This follows the audit of 2026-10-13 (`docs/research/audit-2026-10-13.md`, taken at `672a26f`). The fix plan for
that audit has landed on this branch, and the NIF team's fixes with it. Of its 21 findings, these are now closed
in the code: 1 (cancelled scan), 2 (BSA folder count), 3 (NIF string count), 4 (graph cycle check), 5 (output
stamp), 6 (unreadable folder), 7 (set views cached), 8 (thumbnails shared and evicted), 9 (parallel hashing),
10 and 11 (undo), 12, 13, 14 (viewport failures listed), 15, 16 (Qt escapes), 17 (scan lock), 18 (fixture case,
corpus skip), 19 (trailing comment), 21, and most of 20. This report does not repeat them. It adds what the six
reviews found beyond that list, and it notes where a 10-13 fix is only partial.

**What this repo does:** `sdc` converts a texture artist's source images (PNG, TGA, EXR, ...) into Skyrim DDS
textures through a native BC encoder layer, with a CLI and an egui GUI that also edits the `sdc.toml` project file,
previews encodes, and shows meshes in a Direct3D 11 viewport. A scanner (`modscan`) reads the user's Mod Organizer 2
instance (BSA archives, NIF meshes, ESP plugins) into a SQLite cache so the GUI can say which mesh uses which texture.

**Load assumed:** one artist on one Windows PC. Texture folders of a few hundred to a few thousand images, up to
8192x8192. Mod folders of 100k+ files with tens of thousands of meshes. Mod content is downloaded from the internet,
so the NIF, BSA and ESP parsers see untrusted input.

**How it was checked:** six parallel reviews (engine image paths; engine config, plan and write layer; FFI and
binary parsers; modscan and pgpsim; GUI; render3d, CLI and bench), each finding re-read in the source, then re-read
again at `ddae78d` after the branch moved. `cargo clippy --tests` is clean on the five crates that build on Linux
(vfs, nif, esp, modscan, pgpsim) and their tests pass. A fuzz harness ran every parser entry point over every file
prefix, 20,000 random byte flips and a u32 blast at every offset: no panics. The vendored encoder objects match
`SHA256SUMS`. Engine, GUI, render3d, CLI and bench need MSVC and were read, not compiled.

## Must fix

1. **A corrupt or hostile mesh can still make the scan allocate gigabytes and abort the process**
   (`crates/nif/src/geom/vertex_desc.rs:86-96`, `crates/nif/src/props.rs:268-276`, `crates/vfs/src/bsa.rs:164`)
   - **What this is:** The 10-13 audit capped the BSA folder count and the NIF string count. Three more places size
     a buffer from a count read out of the file before any content is checked.
   - **Problem:** `read_vertices` reserves up to nine Vecs of `count` entries, then reads vertex 0 and only there
     finds the attributes do not fit the stride. Measured: a 7.8 MB file with `vertex_size = 4` reserved 156 MB
     before `Err("vertex 0: attributes ... need 48 bytes but the vertex size is 4")`; a 100 MB mesh would ask for
     about 2 GB. `decode_texture_set` keeps one `TexPath` (two Strings) per declared slot with no cap: 2,000,000
     empty slots cost 109 MB, passed `finish`, and were stored with no problem reported. `Bsa::read` does
     `Vec::with_capacity(orig)` with `orig` capped at 512 MB, so eight parallel readers of a tiny archive can commit
     4 GB. None of this is a memory-safety bug. But an allocation failure aborts the process, and the
     `catch_unwind` in `crates/modscan/src/scan.rs:81` cannot catch an abort, so the GUI dies mid-scan.
   - **Fix:** In `read_vertices` compute the bytes the enabled attributes need (`16*pos + 4*uv + 4*nrm + 4*tan +
     4*col + 12*skin + 4*eye`) and return `Err` when that exceeds the stride, before the reserves. In
     `decode_texture_set` reject `n > 32` (Skyrim uses 9, Fallout 4 uses 10). In `Bsa::read` use `Vec::new()` or
     cap the capacity at `data.len() * 255`, the largest LZ4 ratio.
   - **If we skip it:** One broken mod in a load order crashes the scanner every time, with no error shown.

2. **Dropping a folder while the "Undecided textures" dialog is open starts an export of the new folder unasked**
   (`crates/gui/src/model/mod.rs:429-441`, `:925`, `:955`; `crates/gui/src/app.rs`, the `dropped_files` handler)
   - **What this is:** `open_folder` clears pending export state. It clears the dialog only when it is
     `OverwriteJson`. When a plan lands, `refresh_undecided_dialog` closes a `ProceedAnyway` dialog whose keys no
     longer exist and calls `continue_export(Recheck)`.
   - **Problem:** Press Export, get the `ProceedAnyway` dialog, then drag another folder onto the window (egui
     delivers drops through a modal). The new folder's plan lands, none of the old keys exist, the dialog closes,
     and `run_continue` runs the undecided check on the new folder. If it has no undecided texture, `start_export`
     saves `sdc.toml` into the new folder and runs a full export the user never asked for.
   - **Fix:** In `open_folder`, set `self.dialog = None` unconditionally. Every dialog that can be open there
     belongs to the previous folder; `OpenUnsaved` and `ExportRunning` are already resolved by then.
   - **If we skip it:** A wrong-folder export writes thousands of DDS files and an `sdc.toml` without a click.

3. **Save and Export write a clean `sdc.toml`, so after a hand edit the dialog's "Overwrite" destroys that edit**
   (`crates/gui/src/model/mod.rs:1684-1690`; `crates/gui/src/ui/dialogs.rs:335`)
   - **What this is:** `AppModel::save` writes the project file whether or not it is dirty. The sets document right
     below it is filtered by `is_dirty()`, with a comment saying why; the project document is not.
   - **Problem:** Open a folder, make no edit, add a `[files]` entry to `sdc.toml` in a text editor, come back and
     press Ctrl+S or Export. Nothing reloads the hand edit, so the plan still ignores it. The save sees the file
     changed on disk and offers "Reload / Overwrite / Cancel". Overwrite writes the stale in-memory copy over the
     hand edit although the GUI had nothing to save. `docs/gui.md` promises this dialog only "while you have
     unsaved edits". `tests/model.rs` covers the dirty case only.
   - **Fix:** In `save()` skip a project that is not dirty, as the sets document already does. On focus regain and
     on Export, treat "changed on disk and not dirty" as a plain reload: `reload()`, clear history, `replan()`.
   - **If we skip it:** A user loses hand-written config by pressing the button the dialog offers.

4. **A packed output path typed in the GUI can equal another job's output; two jobs then write one file**
   (`crates/engine/src/api.rs:813`, `:898`, `:1171-1180`; `crates/engine/src/pack/plan.rs:379`, `:420`;
   `crates/gui/src/model/sets.rs`, the packed-path check that only requires `.dds`)
   - **What this is:** Plan step 5 (`duplicate_outputs_with`) rejects two inputs that map to one output. It runs
     on the file list. `plan_packing` runs later and sets a recipe's output from `packed_outputs`, the user-typed
     path, which the GUI only checks ends in `.dds`.
   - **Problem:** Set `rock` has `rock_n.png` and a raw `rock_roughness.png`. The user types `rock_n.dds` as the
     packed output path. Two `Ready` jobs now target `out/rock_n.dds`. `run` writes both in parallel (the last
     `rename` wins), appends two manifest records for one key, and the next if-changed run compares against
     whichever record is last.
   - **Fix:** After `plan_packing`, run the duplicate check once more over `jobs` by `output_key` (case folded) and
     move clashing jobs to `skipped` with `IN-DUPLICATE`, as step 5 does for files.
   - **If we skip it:** The exported normal map is silently replaced by a packed map, or the other way round.

## Should fix

5. **The sRGB decode and encode loops run one thread over every texel; the swizzle string is re-parsed per texel**
   (`crates/engine/src/ops.rs:59-74`, `:78-93`, `:140-152`; `crates/engine/src/quantize.rs:71-83`;
   `crates/engine/src/mips.rs:66`, `:138`)
   - **What this is:** `preprocess_with` calls `srgb_to_linear` (one `powf`) on RGB of every base texel;
     `to_encoder_input` calls `linear_to_srgb` on every texel of every mip. Both are plain serial loops. The box
     downsample calls the bounds-checked `at()` four times per output texel, also serial.
   - **Problem:** For an 8192x8192 sRGB colour map that is about 450 million `powf` calls on one thread, roughly ten
     seconds per file, while the rayon pool idles; the encoder right after is parallel. A big batch hides some of
     this because files run in parallel, but a single file (the GUI preview path, and the tail of every batch)
     pays it in full. `swizzle(*px, s)` runs `s.chars()` and a `match` for every texel when a swizzle is set.
   - **Fix:** `par_iter_mut()` in `preprocess_with` and `par_iter()` in `to_encoder_input` (rayon is already used
     next door in `encode.rs` and `filter.rs`). For 8-bit stored sources a 256-entry lookup table is exact.
     Resolve the swizzle string into `[u8; 4]` once before the loop. In `downsample`, take two source rows as
     slices per destination row instead of `at()` per texel, with `par_chunks_mut` per row.
   - **If we skip it:** Preview latency and batch tails stay several seconds longer than needed on big textures.

6. **Image loading and decoding hold two or three full-size copies at once**
   (`crates/engine/src/load.rs:72-85`; `crates/engine/src/dds.rs:737`; `crates/engine/src/decode.rs:54-56`,
   `:119`; `crates/engine/src/resize.rs:39-44`)
   - **What this is:** `load_image` decodes to the native depth, calls `to_rgba32f()` (copy one), then
     `.pixels().map(|p| p.0).collect()` (copy two) while `img` stays alive for `width()`. `read_dds` does
     `bytes[off..].to_vec()` while the caller still owns `bytes`. The RGBA8 decode arm does `data.to_vec()` and
     then `quads()` copies again. A non-box resize computes a full f64 area pass for RGB and then overwrites the
     RGB with the filtered result.
   - **Problem:** An 8192x8192 RGBA16 PNG holds 512 MiB + 1 GiB + 1 GiB at the collect; one gigabyte per
     in-flight file that the admission budget does not count, so fewer files fit. The DDS path holds the file
     bytes twice. The Kaiser resize does the whole area pass for nothing.
   - **Fix:** Read `width`, `height` and `color()` first, then `img.into_rgba32f().into_raw()` and one
     `as_chunks::<4>().0.to_vec()`. Make `read_dds` take the `Vec<u8>` and `drain(..off)`. Use
     `data.as_chunks::<4>().0.to_vec()` directly in the RGBA8 arm. Give `area_resample` an `alpha_only` flag.
   - **If we skip it:** Peak memory per file is two to three times what the budget estimate assumes.

7. **Plan time still grows much faster than the file count (the glob cache closed only one of four cases)**
   (`crates/engine/src/overrides.rs:58-62`; `crates/engine/src/bake/plan.rs:87-112`, `:305-325`;
   `crates/engine/src/pack/plan.rs:399`, `:445-452`, `:578`; `crates/engine/src/api.rs:1951-1953`)
   - **What this is:** Planning resolves the profile for every file. Rule globs are now compiled once per thread.
     Three other per-file costs remain.
   - **Problem:** `project_rel` makes two `std::path::absolute` syscalls (GetFullPathNameW) per `[files]` override
     per file per layering; a project with 1,500 overrides costs thousands of syscalls per file. `sibling_outside`
     runs `read_dir` plus `is_file()` on every entry once per roughness member whose `_n` is not in the batch, so
     2,000 such sets in one flat folder of 6,000 files is 12 million `stat` calls. `own_normal`,
     `roughness_members`, `plan_packing` and `map_members` each scan the whole job or skipped list per set or
     member (`rnm/plan.rs` already builds a by-set index; these do not), and `failed`/`cancelled` are `Vec<PathBuf>`
     searched linearly. The GUI re-plans on every edit.
   - **Fix:** Compute the project-relative path once per file into `FileFacts`. Cache directory listings per folder
     in `plan_bakes` (use `DirEntry::file_type()` instead of `is_file()`). Build a `BTreeMap<&str, Vec<usize>>` by
     set once, a `HashSet<&Path>` of skipped inputs once, and take `failed`/`cancelled` as sets.
   - **If we skip it:** A 10,000-file folder takes minutes to plan and every GUI edit stalls for seconds.

8. **The settings panel deep-clones the job and serialises its profile up to eleven times per frame**
   (`crates/gui/src/ui/settings_panel.rs:815-835`; `crates/gui/src/model/fields.rs:156`, `:221`)
   - **What this is:** `draw` clones `item.job` (profile, provenance map, suggestions, warnings, pack, rnm) to end a
     borrow, then each field group calls `field_views`, which does `serde_json::to_value(&job.profile)`;
     `levels_view`, `filter_view` and `edge_view` are extra calls, and the Advanced drawer adds three more.
   - **Problem:** While any texture is selected, every frame allocates a deep copy of a multi-KB struct and 8 to
     11 JSON serialisations, for a panel that only changes on edits.
   - **Fix:** Hold `job: Option<Arc<ResolvedJob>>` in `TextureItem` (the thumbnail already went this way); call
     `field_views` once per `draw` and filter per group.
   - **If we skip it:** Idle CPU and allocator churn whenever a texture is selected.

9. **The encoded preview keeps a full f32 decode of every mip, twice while re-encoding**
   (`crates/gui/src/model/preview.rs:32`, `:212`, `:231`; `crates/gui/src/worker.rs:218`)
   - **What this is:** `spawn_encode` eagerly decodes every encoded mip into `Vec<Vec<[f32; 4]>>` (16 bytes per
     pixel). Only `heatmap_of` (one mip) and the CPU upload fallback read it. `EncodedState::Encoding { previous }`
     keeps the old result while the new one is made.
   - **Problem:** At the default 4096 limit mip 0 alone is 268 MB and the chain about 358 MB, next to the f32
     source preview; a second encode of a 4096 texture holds over 1 GB, four times that at 8192.
   - **Fix:** Decode lazily per level (`OnceLock` per mip, or decode the requested mip in `heatmap_of`), or
     store `[u8; 4]` or f16.
   - **If we skip it:** Live encode on a large texture pushes a 16 GB machine into swapping.

10. **A `[files]` key written with backslashes never matches, and the only warning is hidden**
    (`crates/engine/src/overrides.rs:26-43`)
    - **What this is:** `path_key_matches` lower-cases the key and compares it to the slash-separated relative
      path. `fold_id` for set ids normalises `\`; this function does not.
    - **Problem:** A hand-edited `sdc.toml` on Windows with `[files.'armor\iron_n']` (a TOML literal string, the
      natural way to type a Windows path) applies nothing. The only signal is `CFG-FILE-UNMATCHED`, an Info code
      the CLI's human log does not print (DECISIONS S-mips-13). The user's per-file setting is silently ignored.
    - **Fix:** `let k = key.replace('\\', "/").to_lowercase();` at the top of `path_key_matches`. Add a test in
      `tests/file_scopes.rs` with a backslash key.
    - **If we skip it:** Hand-written overrides look accepted and do nothing.

11. **CLI report verbs panic on a closed stdout and exit 3**
    (`crates/cli/src/verbs.rs:132-401` (49 `println!` sites), `:590-596`; `crates/cli/src/main.rs:79-88`)
    - **What this is:** `inspect`, `validate`, `presets` and `patch-header` print with `println!`.
    - **Problem:** `sdc validate *.dds --json | head -n1` closes the pipe after one line; the next `println!`
      panics ("failed printing to stdout"), `catch_unwind` reports "sdc: internal error" and exit 3, the fatal
      code. The engine's `JsonLinesSink` already ignores write errors on purpose; the verbs' own lines do not.
    - **Fix:** Make `say()` the only stdout writer (`let _ = writeln!(stdout.lock(), ...)`) and route the
      `println!` sites through it.
    - **If we skip it:** Scripts that pipe `sdc` output into `head` or a pager get the fatal error code.

12. **In the 3D viewport, a texture edit after a shader change leaves the shape failed with no job queued**
    (`crates/render3d/src/lib.rs:1290-1308`)
    - **What this is:** `apply_in_place` handles the `Textures` edit path. On `Lookup::Waiting` it compiles inline
      only in sync mode; in async mode (the GUI) it returns `Err("the program is not compiled")`.
    - **Problem:** GUI → `set_shaders` with changed sources (programs cleared) → the user changes a texture slot →
      `classify` is `Textures`, the shape is still `Drawing`, so no rebuild → `Err` → `ShapeStatus::Failed`. No
      compile job is queued, so the shape never recovers until a full reload. The only test for this sequence
      (`tests/async_compile.rs`) runs in sync mode.
    - **Fix:** On `Lookup::Waiting` with `self.async_compile`, call `self.begin(id, m, textures, rep)` and return
      `Ok(())`, as the `Permutation` path does.
    - **If we skip it:** Editing a texture right after a shader reload shows a red shape until the user reloads.

13. **Risky paths with no test that fails when they break**
    - **What this is:** The suites are large and good on layouts and edge sizes. These branches have none:
      `[files]` keys with `\` (10); a packed output path equal to another output (4); the "Overwrite" answer of
      the external-change dialog (3); folder drop while `ProceedAnyway` is open (2); the BSA reader with
      truncated or fuzzed input (`crates/vfs/tests/bsa.rs` has four hostile cases, no prefix sweep); esp with more
      than one cut; `nif::scan`, `read_graph`, `decode_*` and `Bsa::read` with a prefix sweep (only `read_shape`
      has one); a scan that walks a real BSA (every `.bsa` fixture in modscan is an empty file); a changed file
      with the same length and mtime second (14); `Renderer::render` at 0x0; the render3d async texture edit (12).
    - **Problem:** Each must-fix above would have been caught by a ten-line test next to the existing ones, and
      the parsers' current robustness has no regression guard.
    - **Fix:** One `for cut in 0..=bytes.len()` loop per parser over the existing builders, asserting "returns,
      never panics"; one fixture test per item above.
    - **If we skip it:** The next refactor of `each_sub` or `Bsa::open` ships a panic on a mod file.

## Pitfall scan (what was looked for, what was found)

The request named the usual signs of machine-generated Rust. Checked across all source at `ddae78d`:

- **`unwrap`/`expect` on user data:** none found. The engine's sites are on closed enums, lengths already checked,
  or lock poisoning (`unwrap_or_else(|e| e.into_inner())`). The guarded `unwrap` in `dds_patch.rs` follows a
  length check.
- **Swallowed errors:** every `let _ =` site was read. Each is a deliberate "closed pipe is not an engine
  failure", a cleanup after a failure, or a channel send to a receiver that may have gone. The three worth a
  banner are in finding 14.
- **`unsafe`:** about 60 blocks (42 in render3d, 11 in encoders-sys, 5 in modscan, 2 in engine). Each has a true
  SAFETY note; buffer byte counts, strides and lifetimes line up; HRESULTs are propagated or dropped on purpose.
  The one wrong comment (backdrop constant buffer "64 bytes", it is 80) is listed among the left-out items.
- **`clone()` for the borrow checker:** about 440 in the GUI, 285 in the engine. Most are small ids and paths. The
  ones that matter are findings 8 and 14 (job per frame; path keys per scan). Thumbnails were fixed on 10-13.
- **Heap allocation in hot loops:** findings 5, 6, 9 and 14 (per-texel string parse, double image copies, f32
  mips held, per-block `to_vec` in the bench, per-record folder-name clone in the BSA reader).
- **Needless `Arc<Mutex<>>`, `Rc<RefCell<>>`, traits with one implementation, string-matched errors:** none
  found. Errors are typed with `thiserror`; the event sink trait has four real implementations.
- **Integer casts:** header fields go through `checked_*` arithmetic in `dds.rs` and the NIF cursor; the one
  silent `as u32` (bc7e block count) is unreachable below 64 GB of pixels.
- **`#[allow]`:** seven, all `too_many_arguments`, `type_complexity` or `large_enum_variant`. No `dead_code` allow.
- **Clippy:** clean on the five crates that build on Linux. The others need MSVC and were not compiled here.

**Verdict:** Healthy core with the 10-13 fixes in. Fix the parser allocation caps (1) first, then the three
data-touching GUI and plan bugs (2, 3, 4); the rest is throughput and memory on large folders.

**Lean:** about -200 lines, -1 duplicate dependency build (`toml_edit` x2), -5 schema columns possible.

**Not checked:** `crates/encoders-sys/vendor/**` beyond the headers and `SHA256SUMS`; engine, GUI, render3d, CLI
and bench were read but not compiled or run; the GUI drawing code in `ui/*` was skimmed for per-frame patterns,
not read line by line; `crates/gui/tests/*`, `crates/engine/tests/*` and `crates/cli/tests/*` were grepped for
coverage, not read; the ~170 files that changed between `672a26f` and `ddae78d` were re-checked only where a
finding pointed at them.
